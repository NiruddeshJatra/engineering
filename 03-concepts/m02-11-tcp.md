# 11. TCP: turning a lossy network into a reliable stream

*Where we are: DNS has given the laptop `bhara.com`'s address. Before it sends the request for the page, it sets up a connection with the server. This note is about what that connection is and why it's needed.*

## The problem: IP makes no promises

IP is **best effort** (note 3). It tries to deliver each datagram and promises nothing. On the way:

- datagrams get **lost** when a router's queue is full (note 2),
- they arrive **out of order** when they take different paths or wait in different queues,
- they occasionally get **duplicated**,
- bits can be **corrupted**.

A web page, a file or a login request can't tolerate any of that. A 100 KB page travels as about 70 separate pieces. If one is missing, the page is broken; if two are swapped, the HTML is garbage.

Something has to turn "probably delivered, in some order" into "every byte, exactly once, in order." That's **TCP** (*Transmission Control Protocol*).

### Why not fix this inside the network?

Because only the two ends can know whether the whole transfer succeeded (note 3), and because routers that tracked every conversation would be slow and expensive. Keeping the core simple and putting reliability in the end hosts has another benefit: applications that don't want reliability, like voice calls, don't have to pay for it. They use UDP (note 4).

## "Which conversation": what a connection is

> [!question] You asked (ChatGPT)
> "Transport — Which conversation. Here, what do you mean by "which conversation"?"
>
> "What does relevant connection mean here? Why does tracking bytes and handling retransmission needed? How can the software or device handling TCP know that a packet is lost or haven't successfully transmitted?"

Your browser often has several connections open to the same server at once, and the server has thousands with different clients. Each one is a separate **conversation** with its own bytes to track. A **TCP connection** is that conversation: some memory (state) kept by *both* end machines' operating systems, holding which bytes have been sent, which have been confirmed, which have arrived, and buffers for data in transit. It's identified by the four values from note 4: source IP, source port, destination IP, destination port.

Nothing in the middle of the network knows the connection exists. Routers just see datagrams. The connection lives only at the two ends.

The rest of this note answers the second question: why track bytes, and how TCP knows something is lost.

## Setting up: the three-way handshake

Before any data flows, the two operating systems exchange three small segments:

1. **SYN** (client → server): "I want to connect. My bytes will be numbered starting from *x*."
2. **SYN-ACK** (server → client): "OK. Mine will start from *y*. I got your *x*; I expect *x*+1 next."
3. **ACK** (client → server): "Got your *y*; I expect *y*+1 next."

Why three? Each direction needs two things: one side announces its starting number, and the other side confirms it heard it. That's four messages, and the server combines its confirmation with its own announcement into one (the SYN-ACK). Three is the minimum that lets *both* sides know that *both* directions work.

Why random starting numbers rather than 0? So that a delayed segment from an *old* connection between the same two ports can't be mistaken for data in a new one, and so an attacker who can't see the traffic can't easily guess the numbers and inject fake segments.

The cost: one full round trip before the first byte of the request can be sent.

## The TCP header

| Field | What it's for |
|---|---|
| Source port, destination port | Which programs (note 4) |
| Sequence number | Which bytes this segment carries |
| Acknowledgment number | The next byte I expect from you |
| Flags | SYN, ACK, FIN (finish), RST (abort), and others |
| Receive window | How much more data I can accept right now |
| Checksum | Detects corrupted segments |
| Options | e.g. maximum segment size |

At least 20 bytes. The rest of the note explains the fields one by one.

## Numbering bytes, not segments

TCP treats the application's data as one long **stream of bytes** and numbers every byte. Each segment says "I carry bytes 1,001 to 2,460."

How big is a segment? A typical link carries at most 1,500 bytes per frame (the link's **MTU**, maximum transmission unit). Subtract 20 bytes of IP header and 20 of TCP header, and you get about **1,460 bytes of data per segment**, the **MSS** (maximum segment size). TCP cuts the stream into pieces of that size.

The receiver answers with **acknowledgments (ACKs)**. An ACK says "I have everything up to here; send me byte *n* next." This is called *cumulative*: one ACK confirms all bytes before *n*.

TCP doesn't send one segment and then wait. That would waste most of the time sitting idle (one round trip per segment). It sends a whole **window** of segments, keeps copies of everything not yet acknowledged, and slides forward as ACKs arrive.

## How TCP knows a segment was lost

TCP has two signals.

**1. The timer (retransmission timeout).** Whenever the sender has unacknowledged data, a timer is running. TCP keeps measuring how long round trips actually take, and sets the timeout a bit longer than that. If the timer runs out with no ACK, the sender assumes the oldest unacknowledged segment was lost and sends it again.

**2. Duplicate ACKs (fast retransmit).** The timer is slow, so TCP also watches the ACKs. Here's what happens when one segment in the middle is lost:

```
Sender sends:   [1–1000] [1001–2000] [2001–3000] [3001–4000] [4001–5000]
Lost:                     ✗ 1001–2000
Receiver gets 1–1000            → ACK "send 1001"
Receiver gets 2001–3000         → ACK "send 1001"   (duplicate 1)
Receiver gets 3001–4000         → ACK "send 1001"   (duplicate 2)
Receiver gets 4001–5000         → ACK "send 1001"   (duplicate 3)
Sender: three duplicates → resend 1001–2000 now, without waiting for the timer
```

The receiver keeps saying "I still need 1001," because the later segments arrived but the gap is still there. Three repeats are a strong hint that one segment is missing while the rest of the path works. The receiver buffers bytes 2,001–5,000; when 1,001–2,000 finally arrives, it can hand all of 1–5,000 to the application at once.

That's also the answer to Gemini's quiz question you never replied to: *"If an IP packet carrying bytes 1001–2000 gets dropped by a congested router, which protocol notices, and how does it fix it?"* TCP at the sender notices, through duplicate ACKs or the timer, and retransmits those bytes. IP never notices anything.

### The other problems, solved by the same machinery

- **Corruption:** the receiver checks the checksum; if it fails, it silently throws the segment away. From then on it's just a lost segment, handled as above.
- **Duplicates:** the receiver already has those byte numbers, so it discards the copy.
- **Reordering:** out-of-order bytes wait in the receiver's buffer until the gap before them is filled; the application only ever sees bytes in order.

> [!question] You asked (Gemini)
> "How does reassembly get assured?"

By the byte numbers. Every byte has a position in the stream, so the receiver always knows exactly where each arriving piece fits and what is still missing.

## Two different speed limits

TCP must also decide **how fast to send**. There are two separate dangers, and TCP has a separate mechanism for each. Mixing them up is one of the most common mistakes.

**Flow control protects the receiver.** The receiving machine has a buffer for each connection. If the application is slow to read (a busy phone, a slow program), the buffer fills. So every segment the receiver sends carries a **receive window**: "I have room for this many more bytes." The sender never has more unacknowledged data in flight than that. The receiver states the limit directly.

**Congestion control protects the network.** Even if the receiver has plenty of room, the routers in between may not. If every sender blasted as fast as possible, queues would overflow and most traffic would be lost. Nobody tells the sender about this directly, so TCP has to *infer* it. The sender keeps its own estimate, the **congestion window**:

- A new connection starts small and roughly **doubles** its window every round trip (*slow start*, a misleading name, since growth is fast).
- After that, it grows slowly, by about one segment per round trip.
- When it detects loss, it takes that as a sign of a full queue somewhere, and **cuts** its window sharply (classic TCP halves it).

That's why a lost packet slows a download: TCP is backing off so the network doesn't collapse. A dropped packet is the network's only way of saying "slow down" (note 2).

| | Flow control | Congestion control |
|---|---|---|
| Protects | The receiver's buffer | The network's queues |
| Limit set by | The receiver, stated in every segment | The sender, inferred from loss (and, in some versions, rising delay) |
| Variable | Receive window | Congestion window |

The sender obeys whichever is smaller.

## A stream has no message boundaries

This consequence will matter directly in Unit 4.

TCP delivers a **stream of bytes**, not a sequence of messages. If a program writes 500 bytes and then 300 bytes, the other side might read 800 bytes at once, or 200 and then 600, or 500 and 300. TCP keeps the bytes in order, but it doesn't preserve where one write ended and the next began.

So any application that sends messages over TCP must mark the boundaries itself: "this message ends here." HTTP does that with a blank line and a length field (note 13). A server that assumes "one read = one complete request" works on your own laptop and then breaks on a real network.

## Ending a connection

Each side sends a **FIN** when it has nothing more to send, and the other side acknowledges it, so closing takes up to four segments. The side that closes first keeps a record of the connection for a short time afterwards (the *TIME_WAIT* state) so that stray late segments don't confuse a new connection that reuses the same ports. An **RST** aborts a connection immediately ("connection reset").

## "Reliable" doesn't mean "guaranteed"

TCP can't deliver through a dead link. If acknowledgments stop coming, it retries with longer and longer waits, then eventually gives up and reports an error to the application: "connection timed out" or "connection reset." Reliable means: *every byte arrives, in order, exactly once, or you're told it didn't.* The old article's "certified mail, guaranteed delivery" was overstating it.

## TCP and UDP side by side

| | TCP | UDP |
|---|---|---|
| Connection setup | Three-way handshake | None |
| Delivery | Every byte, in order, or an error | Best effort, no ordering |
| Loss recovery | Timer and duplicate ACKs | None |
| Speed control | Flow and congestion control | None |
| Data model | Byte stream, no boundaries | Separate datagrams, boundaries kept |
| Header | 20+ bytes | 8 bytes |
| Typical use | Web, email, file transfer | DNS, DHCP, voice, games, QUIC |

## Slips to avoid

- **"TCP guarantees delivery."** It guarantees order and completeness, or an error.
- **Flow control and congestion control are not the same thing.** One protects the receiver; the other protects the network.
- **"TCP numbers segments."** It numbers bytes.
- **"One send = one receive."** TCP is a stream; boundaries are the application's job.
- **"MTU is 1,460."** MTU (link limit) is typically 1,500; MSS (TCP data per segment) is about 1,460.

## Try it

With Wireshark capturing, set the display filter `tcp.flags.syn == 1` and load a website: you'll see SYN and SYN-ACK pairs. Then right-click one packet → *Follow → TCP Stream* to see the whole conversation, or filter with `tcp.analysis.retransmission` or `tcp.analysis.duplicate_ack` while downloading something large on weak Wi-Fi.

> [!success]- Answers
> 1. State (sequence numbers, buffers, timers) kept by the two end machines' operating systems, identified by the four-value tuple. Nothing in the network knows it exists.
> 2. Each direction needs an announcement and a confirmation; the server combines its confirmation with its own announcement. Random numbers stop old delayed segments being mistaken for new data and make injecting fake segments harder.
> 3. Timer: no ACK before the retransmission timeout → resend the oldest unacknowledged segment. Duplicate ACKs: later segments arrive, the receiver keeps acknowledging "send 1001"; three duplicates → resend immediately.
> 4. Flow control protects the receiver's buffer; the receiver states its window in each segment. Congestion control protects the network's queues; the sender infers it from loss (or delay) and adjusts its own congestion window.
> 5. TCP is a byte stream that doesn't keep write boundaries; data may arrive split or merged. The application must find message boundaries itself (as HTTP does with a blank line and a length).
