# 10. DNS: from a name to an address

*Where we are: we now know how any datagram gets from your laptop to any IP address. But you didn't type an IP address. You typed `bhara.com`. So the very first datagram your laptop sends for this page isn't to Bhara at all. It's a question: "what is the address of `bhara.com`?"*

## The problem: names for people, numbers for routers

Routers forward by IP address prefix (note 9). People remember names. Something has to translate.

Why not just make routers understand names? Four reasons:

1. **Names don't describe location.** `.com` sites are hosted all over the world, so a router can't summarise "everything ending in `.com` goes that way." IP prefixes can be summarised because they follow networks (note 8).
2. **Fixed-size numbers are fast.** A 32-bit address can be matched in hardware in nanoseconds. Variable-length text can't.
3. **Indirection is useful.** A name can point to different addresses over time, or to several at once. Bhara can move to a new server, or serve Asian users from Singapore and European users from Frankfurt, without anyone changing what they type.
4. **Separation of jobs.** Names are chosen for humans and stay stable for years. Addresses are chosen for routing and change when infrastructure changes.

The system that translates names to addresses is **DNS** (*Domain Name System*). It's an application-layer protocol: like HTTP, it runs in programs at the edges, not in routers.

## The design problem: one giant phone book won't work

A single central database for every name on Earth would fail in every way: one point of failure, impossible traffic load, slow for everyone far from it, and nobody would agree on who runs it. So DNS is **distributed and hierarchical**: the work is split by the structure of the name itself, read from right to left.

```
                    . (root)
                 /     |      \
              com     org     bd   …          ← top-level domains (TLDs)
             /   \
        bhara   google  …                     ← second-level domains
          |
         www  api  …                          ← names inside the domain
```

Three kinds of servers, each knowing only its own level:

- **Root servers** know which servers are responsible for each top-level domain (`.com`, `.org`, `.bd`). There are 13 named root server identities, but each is copied to many places around the world under the same address (anycast, note 9), well over a thousand copies in total.
- **TLD servers** know which servers are responsible for each domain under them. The `.com` servers know who to ask about `bhara.com`, but not `bhara.com`'s address.
- **Authoritative servers** hold the actual records for a domain. Bhara's DNS provider's servers know `bhara.com`'s real address.

## The resolution path

Your Kurose-era summary had this chain exactly right, from memory:

> "DNS → Browser cache → OS cache → DNS Resolver → Root DNS server → TLD server → Authoritative Name server"

Here's what each step does and why.

1. **Browser cache.** Has this browser looked up `bhara.com` recently? If so, done.
2. **Operating system.** The OS has a small piece of DNS software called a **stub resolver**. It checks the OS cache (and the local `hosts` file). If it has an answer, done.
3. **Recursive resolver.** Otherwise the OS sends one question to the DNS resolver address it got from DHCP (note 5). This resolver does the hard work on your behalf.

> [!question] You asked (ChatGPT)
> "So, DNS resolver address can the the IP address of the router, or of the ISP, correct?"

Correct. At home it's usually the router's address. The router then forwards the question to the ISP's resolver, or to a public one such as Cloudflare's `1.1.1.1` or Google's `8.8.8.8` if you've configured that.

4. **The resolver walks the hierarchy**, unless it already has the answer cached:
   - It asks a root server: "Where's `bhara.com`?" The root replies: "I don't know, but here are the `.com` servers."
   - It asks a `.com` server. That replies: "Here are `bhara.com`'s authoritative servers."
   - It asks Bhara's authoritative server. That replies with the address.
5. **The answer comes back** to your OS, then to your browser, and **everyone along the way caches it**.

Your laptop asked one question and received one final answer: that's a **recursive** query ("find it for me"). The resolver asked a sequence of servers, each of which pointed it onward: those are **iterative** queries ("tell me who to ask next").

Not every link in the chain caches. The resolver, your OS and your browser cache answers. The root and TLD servers don't cache Bhara's address; they only ever hand out referrals. (One of the old articles said the TLD servers cache it; they don't.)

## Records and TTL

DNS stores **resource records**. The ones you'll meet:

| Type | Maps a name to | Example use |
|---|---|---|
| **A** | an IPv4 address | `bhara.com → 203.0.113.40` |
| **AAAA** | an IPv6 address | the IPv6 equivalent |
| **CNAME** | another name (an alias) | `www.bhara.com → bhara.com` |
| **NS** | the authoritative servers for a domain | used in referrals |
| **MX** | the mail servers for a domain | where email for `@bhara.com` goes |
| **TXT** | arbitrary text | domain ownership checks, email security |

Every record carries a **TTL** (*time to live*), in seconds: how long anyone may cache it before asking again. (It's a different TTL from the hop counter in the IP header in note 9. Same name, different idea.) A long TTL means fewer lookups and faster browsing, but changes take longer to reach everyone. A short TTL means changes spread quickly, at the cost of more lookups.

That's why the full walk through root, TLD and authoritative servers is rare. For a popular site, the resolver almost always has the answer cached, and most lookups finish in a few milliseconds.

## What DNS rides on

A DNS question and its answer are each usually small enough to fit in one datagram. So DNS normally uses **UDP** on port 53 (note 4): one datagram out, one back, no connection setup. If no answer comes, the stub resolver simply asks again.

DNS switches to **TCP** when an answer is too large for one UDP datagram, and for copying whole zones between servers. Two newer variants encrypt DNS so that your ISP can't read your lookups: DNS over TLS and DNS over HTTPS (note 12 explains TLS). Without them, anyone on the path can see every name you look up, even if the website itself uses HTTPS.

## One name, many addresses

A lookup can return several addresses. Large sites do this for load spreading and backup. Some DNS providers also answer differently depending on where the question comes from, steering you to a nearby server (sometimes called GeoDNS). And some sites use a single **anycast** address that many locations share, like the one in your traceroute (note 9). Either way, the name stays the same while the machine you reach depends on where you are.

## When DNS fails

If the name doesn't exist, the authoritative server says so (an answer called *NXDOMAIN*), and that negative answer is cached too. Your browser shows something like "This site can't be reached… DNS_PROBE_FINISHED_NXDOMAIN." If the resolver itself is unreachable, nothing resolves at all, even though your connection works. That's why "DNS is down" feels like "the Internet is down."

## Slips to avoid

- **"DNS delivers the web page."** DNS only finds the address. The page comes over a separate connection (notes 11–13).
- **"DNS always uses UDP."** Usually, not always: TCP for large answers, and encrypted variants exist.
- **"Every server in the chain caches the answer."** The resolver, OS and browser do. Root and TLD servers give referrals.
- **"DNS TTL = IP TTL."** One is a cache lifetime in seconds, the other a hop counter.

## Try it (Windows)

```
nslookup bhara.com
nslookup -type=NS bhara.com
nslookup -type=MX gmail.com
ipconfig /displaydns
ipconfig /flushdns
```

`nslookup` asks your configured resolver. `ipconfig /displaydns` shows your OS cache, including each entry's remaining TTL. To watch the full walk from the root, use `dig +trace bhara.com` in WSL or Git Bash, or capture with Wireshark using the filter `dns` while visiting a site you haven't opened recently.

> [!success]- Answers
> 1. Names don't follow network location, so they can't be summarised into prefixes; fixed-size numbers can be matched in hardware quickly; names should stay stable while addresses change.
> 2. Browser cache → OS stub resolver (cache, hosts file) → recursive resolver (from DHCP) → root (refers to `.com`) → `.com` TLD (refers to Bhara's authoritative servers) → authoritative server (answers) → cached on the way back.
> 3. Recursive: "give me the final answer." Iterative: each server answers with a referral to the next server to ask.
> 4. One small question and one small answer: a connection would double the cost, and the client can simply retry. TCP for answers too large for one datagram and for zone transfers.
> 5. How long the answer may be cached. Long: fewer lookups, slower to propagate changes. Short: changes spread fast, more lookups.
